Architecture diagrams for people who explain systems

Diagrams that are alive.

An orrery is a working model of the heavens: turn the crank and the planets move. Orrery does the same for your architecture. Write the model as a file, and the diagram animates its traffic and plays the failures you wrote, in your organisation's own words.

Why a model

Not a picture of the system. A model of it.

Orrery is a way to model your system: the components, how they connect, and what happens when something fails. Views are drawings of that model. Change the model and every view changes with it.

Written, not drawn

A JSON file names components, connections, groups and states. Layout is automatic and deterministic, so the same file always renders the same bytes and a diff in review is a diff in meaning.

Alive

Traffic flows along connections at the load you declared. A scenario is the story you tell, step by step: which component fails, what that does to the others, where the traffic goes. The diagram plays it.

In your words

Healthy, impaired, brownout, outage: your states, your kinds, your meanings. Nothing in the tool reads a name or works out a state for you, and the legend teaches every reader your vocabulary.

Turn the crank

Fail the primary. Show what happens.

Nothing here was drawn by hand. One scenario step says the primary database failed, the checkout API is degraded because it reads from the replica, the storefront is degraded because checkout is slower, and the failover line now carries the reads. The figure plays that step on a timer, with no script.

"scenarios": [ { "id": "db-fails", "steps": [ {
  "note": "Orders DB goes down",
  "set": {
    "failed":   "db",
    "degraded": { "api": "reads from the replica; writes are queued",
                  "web": "checkout is slower" }
  },
  "load": [ { "id": "failover", "load": 0.6 } ]
} ] } ],
"views": [ { "id": "loop", "play": { "scenario": "db-fails", "seconds": 3 } } ]

That is the whole of it. A step puts entities in states, each with a reason if you want one, and sets the loads that move. Steps are cumulative and restore undoes them; a view that plays a scenario carries every step as a layer and cycles them with CSS, so it moves wherever an image can be shown.

Try a what-if without writing a scenario: orrery render app.json --set failed=db. In the interactive file, click the component.

Your vocabulary

Degraded means something different at every company.

So the tool does not define it. You bind your own state names to looks, and your own kinds to glyphs, frames and lines. Below, the same checkout in one company's words: healthy, impaired, brownout, outage and drained. For this team the session cache is a nice-to-have, so draining it is a brownout, not an outage.

"states": {
  "default": "healthy",
  "replace": true,
  "define": {
    "healthy":  {},
    "impaired": { "look": "warn" },
    "brownout": { "look": { "stroke": "#7c3aed", "pulse": true } },
    "outage":   { "look": "alert", "flows": "stop" },
    "drained":  { "look": "muted", "flows": "stop" }
  }
},
"kinds": { "connections": {
  "gossip": { "line": { "dash": "2 3", "stroke": "#0891b2" } }
} }
  • Look

    How a state is drawn: a preset, or your own stroke, fill, text, dash and pulse.

  • Flows

    Whether traffic is still drawn moving through an entity in this state.

  • Line

    How a connection kind is drawn: a preset, or your own stroke, width, dash pattern and flow colour.

  • Description

    What the word means to your team. It goes in the legend, for the reader.

Drill down

Close what the reader does not need yet.

A view can draw a group closed: its real footprint with its name and a count, members hidden, connections into it stopping at its frame. It is all one drawing, so opening a group is a camera move, not a new picture. The figure plays a four-scene story with no script: the camera closes on the session cache and its two nodes appear, one node fails in there, and the camera pulls back with the closed box and the API that needs it turned amber. The interactive file plays the same scenes with its camera until you click, and a click on any closed group focuses it.

"views": [ { "id": "overview", "collapse": ["sessions"] } ],
"tour": { "seconds": 4, "scenes": [
  { "view": "overview" },
  { "view": "overview", "focus": "sessions" },
  { "view": "overview", "focus": "sessions", "scenario": "node-fails" },
  { "view": "overview", "scenario": "node-fails" }
] }

One view, one story. A tour lists scenes: a view, a group to focus on, a moment of a scenario, a caption. Nothing is duplicated and nothing can drift: the same components, connections and states draw every scene, so a change to the model is a change to all of them.

One file

The same file, wherever the reader is.

There is no export step and no hosted viewer. The SVG your build produces is animated wherever an image can be shown, and interactive wherever it can be opened.

In a README

GitHub renders it through an image tag. Traffic animates, states show, no plugin, no build, and it reads on a phone.

In a browser

Opened directly, a six-kilobyte runtime inside the file adds an outline, a scenario player, view switching with a morph, drill-down, and a click to step any component through your states.

In review

Views drill into a group or a subset. Any scenario step renders as a static picture, so a design review or an incident writeup shows the exact moment it discusses.

Written by agents, read by humans

Designed so a coding agent gets it right first time.

Every property in the schema explains itself. Unknown properties are errors. Every error is a JSON pointer and a sentence. A fresh agent given only the specification, the schema and the command line has grown a model through every step, from components to a replaced vocabulary, validating first time at each.
