# Contributing to Orrery

Thanks for coming. Orrery is a small project with firm habits; this page is all of them.

## Setup

Node 22 or newer and Yarn 4 (enable it with `corepack enable`).

```sh
yarn install
yarn build          # compiles every package and bundles the runtime
yarn test           # builds, then runs everything: unit, contract, snapshot, pixel and CLI tests
yarn check          # typecheck, lint and test, what CI runs on a pull request
```

`yarn inspect <file>` renders a model, freezes animation frames to PNG and writes a contact sheet, so you can look
at what you changed. `yarn examples` regenerates every picture in the README and the reference pages.

## How changes land

1. **A failing test first.** Every behaviour is a test before it is code; there are no exceptions. The suite is
   fast, and the test is the specification of what you meant.
2. **The model is the product.** A change to what a file can say updates [docs/MODEL.md](docs/MODEL.md): the
   field, an invariant with a number and a test, and a decision entry if a direction was chosen over another. The
   schema's description for the field says the same thing in the same words.
3. **Nothing is inferred.** The tool draws what the author declared. A feature that computes a state, guesses a
   meaning from a name, or argues with the author's scenario will not be merged. See MODEL.md §5 and §9.
4. **Look at the picture.** A rendering change regenerates the examples (`yarn examples`) and the pull request
   says what you saw. Frame tooling exists so the change can be checked frame by frame.
5. **Less code with the same behaviour is better code.** Remove what a change makes dead.

Pull requests run typecheck, lint and the full test suite; main requires them to pass. One reviewer, usually the
maintainer, merges. Small pull requests merge fastest.

## The test suites and what each is for

| Suite | Where | Purpose |
|---|---|---|
| Unit and contract | `packages/*/test` | Each package's behaviour, invariant by invariant; the layout contract runs against every engine. |
| Regression (`yarn test:regression`) | `test/orrery/regression.test.ts` | The diagram of Orrery, `examples/orrery.orrery.json`, must use every property the schema offers and every feature by name. A new feature without a place in that diagram fails here. |
| Smoke (`yarn test:smoke`) | `test/orrery/smoke.test.ts` | The built `orrery` command on that diagram, as a user runs it: validate, render, export, embed, packs. |
| Performance (`yarn perf`) | `test/perf` | A frozen benchmark model through every stage, held against a baseline that may only get better: bytes and counts exactly, timings with slack. CI tightens the baseline itself on every push to main; see test/perf/README.md. |
| Integration (`yarn test:integration`) | `test/orrery/integration.test.ts` | That diagram through the whole pipeline in code: every export parses and carries what its kind of picture must, the frame tooling freezes it, the interactive file mounts and the engine drives it. |

The first four run in `yarn test`; the ratchet runs alone after them, in `yarn check` and in CI on every pull request. When you add a feature: a unit test first, then a place for it in the diagram of Orrery, then look at the
regenerated pictures.

## Where things are

| Path | What |
|---|---|
| `packages/core` | schema, validator, declaration, view scoping, renderer, packs, shapes |
| `packages/layout-elk` | the only package that imports elkjs; layout runs behind `LayoutEngine` |
| `packages/runtime` | the engine inlined into every rendered SVG |
| `packages/raster` | freeze, rasterise, frame tooling |
| `packages/cli` | `orrery validate`, `render`, `export`, `embed`, `packs` |
| `docs/MODEL.md` | the specification |
| `examples/` | the README's checkout, the kitchen sink and the moving parts, all regenerated |
| `tools/` | the scripts behind `yarn examples`, `yarn inspect`, the packs and the skill's generated references |
| `plugins/orrery` | the Claude Code plugin: one skill that teaches the model; `node tools/skill-refs.mjs` regenerates its model, examples and errors references, and `test/orrery/skill.test.ts` keeps it valid |

## Vocabulary packs

The cloud packs are the providers' own icon sets, generated by `node tools/packs/build.mjs` and committed. Their
terms are in [docs/PACKS.md](docs/PACKS.md); do not add a set whose terms do not permit redistribution for
architecture diagrams.

## Releasing

Every package shares one version. To release: `yarn workspaces foreach -A version <x.y.z>`, a line in
CHANGELOG.md, commit, `git tag v<x.y.z>`, push the tag. The release workflow runs the full check and publishes
every package to npm with provenance; npm's trusted publishing ties each package to this repository's workflow, so
the workflow uses the NPM_TOKEN repository secret if one is set, else trusted publishing.

## Conduct

This project follows the [Contributor Covenant](CODE_OF_CONDUCT.md). Be kind; assume good faith; argue about the
model, not the person.
